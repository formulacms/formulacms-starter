# Upgrade from formulacms 0.1.0 to 0.1.1

This file moves a site made from formulacms 0.1.0 to 0.1.1. It keeps your own
content types, blocks, text and styling. You can follow it yourself, or give
it to a coding agent. For this upgrade, this file takes precedence over the
general Fork Upgrade Playbook in `docs/starter/operations.md`.

**Kind of upgrade: update.** This release needs no data migration, no
configuration change and no administrator action. It changes no data.
Rollback is a return to your previous commit (see "Roll back" below).

## Read this file from a 0.1.0 site

Your 0.1.0 site does not contain this file. Run these commands in your site's
folder to read it from the 0.1.1 release:

```bash
git remote add starter https://github.com/formulacms/formulacms-starter.git
git remote set-url --push starter DISABLED
git fetch starter --tags
git show v0.1.1:upgrades/v0.1.0-to-v0.1.1.md
```

The fetch can also list `starter/main` and pre-release tags such as
`v0.1.1-rc.1`. Ignore them. If git says that the remote `starter` already
exists, go on to the next command. The second command stops any push to the
starter by mistake. If git says that the folder is not a git repository, go
to "A site without the starter's history" first. Without git, you can read
this file on GitHub:
https://github.com/formulacms/formulacms-starter/blob/v0.1.1/upgrades/v0.1.0-to-v0.1.1.md

## What changes in 0.1.1

- **Restore from Trash.** A restored page keeps a language published when
  another page now uses only the address of its draft. In 0.1.0, that
  language was unpublished. This changes two publication files,
  `convex/cms/publication.ts` and `convex/lib/publishing/snapshots.ts`, and
  `lib/admin/page-address-messages.tsx`. Two new admin messages are in
  `messages/admin/en.json` and `messages/admin/fr.json`.
- **Local setup.** When you give a secret in your shell, `pnpm dev` now keeps
  it exactly as you gave it (`scripts/lib/local-setup.ts`).
- **Hosting guide.** `docs/starter/hosting.md` has two more sentences: wait
  about a minute after the first deploy, and choose your team when
  `vercel link` asks.
- **Packages.** The development package `glob` moves from version 13 to 14.
  This changes `package.json` and `pnpm-lock.yaml`.
- **Upgrade files.** This file is new, and so is `CHANGELOG.md`, which lists
  what changed in each release. `engine.manifest.json` has new path classes:
  `sharedRegistries`, `pathRules` and `defaultRule`. `AGENTS.md` and
  `CLAUDE.md` have one new line that points to the upgrade files.
- **Release records and tests.** The release records `starter.provenance.json`,
  `starter.release-lock.json` and `starter.transitions.json` change, and so
  does `docs/starter/operations.md`. The tests of the changed files change
  too.

## Coding agents: stop and ask the person first

Follow this file step by step. Stop and ask the person before you continue
when any of these happens. A STOP takes precedence over the conflict rules
below.

- The upgrade needs a data migration. This upgrade has none.
- A change touches sign-in: `convex/auth.ts` or `convex/auth.config.ts`.
- A change touches publication: `convex/cms/publication.ts` or anything
  under `convex/lib/publishing/`.
- The next action is a deploy.
- A conflict is in an owner file (see "Conflict rules").
- Both sides changed the same content type or block entry in a different way.
- A content type or block from step 4 is missing after the merge.
- A transition check does not print "Release transition verified", or it
  exits with an error. "Unsupported" is one such case.
- The base is not v0.1.0.
- The next action is the re-parent step or any force-push.
- A check still fails after one repair. A test that already failed before
  the upgrade does not count (see step 14).

## Before you start

- You need git, Node.js and pnpm. Your site's packages must be installed
  (`pnpm install` ran once in this folder).

## Steps

1. Check that your working tree is clean. This command must print nothing:

   ```bash
   git status --short
   ```

2. Add the starter remote and fetch its tags. Use the commands in "Read this
   file from a 0.1.0 site". Skip them if you already ran them.

3. Check that your site is built on v0.1.0:

   ```bash
   git merge-base --is-ancestor v0.1.0 HEAD && echo "base is v0.1.0"
   ```

   If it does not print "base is v0.1.0", go to "A site without the starter's
   history" below.

4. Record your content types and blocks, and the tests that fail, before the
   merge:

   ```bash
   node -e 'const fs=require("fs");const t=f=>JSON.parse(fs.readFileSync(f,"utf8")).map(e=>e.type).sort();console.log(JSON.stringify({contentTypes:t("convex/lib/contentTypes/content-types.manifest.json"),blocks:t("lib/slices/slices.manifest.json")},null,2))' > .git/formulacms-before.json
   pnpm test:run > .git/formulacms-tests-before.txt 2>&1 || true
   ```

   The starter's tests check the starter's own blocks, content types and
   text. On a site that changed them, some tests fail before the upgrade too.
   Step 14 compares the two runs. The test run can take more than 10 minutes.

5. Check that 0.1.1 declares this upgrade. Use the 0.1.1 transition list with
   your current check script. Keep the path relative, as shown:

   ```bash
   git show v0.1.1:starter.transitions.json > .git/formulacms-target-transitions.json
   node --import tsx scripts/check-release-transition.ts --source-tag v0.1.0 --target-tag v0.1.1 --manifest .git/formulacms-target-transitions.json
   ```

   It must print "Release transition verified: v0.1.0 -> v0.1.1 (update; ...)".
   Any other result means STOP. Use `node --import tsx` here, not `pnpm exec`:
   pnpm 11 starts an install before `pnpm exec`.

6. Create an upgrade branch and merge the release without committing:

   ```bash
   git switch -c upgrade/0.1.1
   git merge --no-ff --no-commit v0.1.1
   ```

   When files conflict, git stops and the command fails. That is expected.
   List the conflicts with `git status --short`. Then check for sign-in and
   publication changes. If this command prints a path, STOP:

   ```bash
   git diff --name-only v0.1.0 v0.1.1 -- convex/auth.ts convex/auth.config.ts convex/cms/publication.ts convex/lib/publishing
   ```

   For this release, the command prints two paths:
   `convex/cms/publication.ts` and `convex/lib/publishing/snapshots.ts`. They
   hold the Trash fix from "What changes in 0.1.1": a restored page keeps a
   language published when another page uses only the address of its draft.
   An agent shows this to the person and continues when the person says yes.

7. Resolve each conflict by its class. Read the classes from the 0.1.1
   manifest, because the 0.1.0 copy has only some of them:

   ```bash
   git show v0.1.1:engine.manifest.json
   ```

   Use "Conflict rules" below. After you resolve a file, run `git add <file>`.

8. Resolve `package.json` before `pnpm-lock.yaml`.

9. Regenerate both registries, then check them:

   ```bash
   node --import tsx scripts/sync-content-type-registration.ts
   node --import tsx scripts/sync-slice-registration.ts
   node --import tsx scripts/sync-content-type-registration.ts --check
   node --import tsx scripts/sync-slice-registration.ts --check
   ```

   These are the `pnpm content-types:sync` and `pnpm slices:sync` scripts.

10. Install the packages, then confirm that the lockfile is complete:

    ```bash
    pnpm install
    pnpm install --frozen-lockfile
    ```

    If `pnpm-lock.yaml` still has conflict markers, `pnpm install` removes
    them. pnpm documents this at `https://pnpm.io/git#merge-conflicts`.

11. Run the transition check again, now with the merged files:

    ```bash
    node --import tsx scripts/check-release-transition.ts --source-tag v0.1.0 --target-tag v0.1.1
    ```

    It must print the same "Release transition verified" line as step 5.

12. Record your content types and blocks again, then compare them with step 4.
    The second command must print "Nothing lost.":

    ```bash
    node -e 'const fs=require("fs");const t=f=>JSON.parse(fs.readFileSync(f,"utf8")).map(e=>e.type).sort();console.log(JSON.stringify({contentTypes:t("convex/lib/contentTypes/content-types.manifest.json"),blocks:t("lib/slices/slices.manifest.json")},null,2))' > .git/formulacms-after.json
    node -e 'const fs=require("fs");const r=n=>JSON.parse(fs.readFileSync(".git/formulacms-"+n+".json","utf8"));const a=r("before"),b=r("after");const lost=["contentTypes","blocks"].flatMap(k=>a[k].filter(t=>!b[k].includes(t)).map(t=>k+": "+t));console.log(lost.length?"LOST "+lost.join(", "):"Nothing lost.");process.exit(lost.length?1:0)'
    ```

    New entries from the starter are fine. A missing entry means STOP.

13. Review the starter's changes in owner files. Git merges a change without
    a conflict when you did not edit the same lines. Read these changes and
    keep or undo each one:

    ```bash
    git diff v0.1.0 v0.1.1 -- app/globals.css components/slices convex/lib/slices public
    ```

14. Run the checks. Each one must pass:

    ```bash
    pnpm typecheck
    pnpm lint
    pnpm slices:sync --check
    pnpm content-types:sync --check
    pnpm check:tokens
    ```

    The tests have a different rule: no test may fail that passed before the
    upgrade. Run them again, then compare the run with step 4. The run can
    take more than 10 minutes. The second command must print
    "No new failures.":

    ```bash
    pnpm test:run > .git/formulacms-tests-after.txt 2>&1 || true
    node -e 'const fs=require("fs");const r=n=>fs.readFileSync(".git/formulacms-tests-"+n+".txt","utf8").replace(/\x1b\[[0-9;]*m/g,"").split("\n");const after=r("after");if(!after.some(l=>l.trim().startsWith("Test Files"))){console.log("The test run did not finish. Run it again.");process.exit(1)}const fails=lines=>new Set(lines.filter(l=>l.startsWith(" FAIL ")).map(l=>l.trim()));const before=fails(r("before"));const added=[...fails(after)].filter(l=>!before.has(l));console.log(added.length?"New failures:\n"+added.join("\n"):"No new failures.");process.exit(added.length?1:0)'
    ```

    A test that also failed in step 4 fails because of your own change. It is
    not a STOP: list it in the commit and fix the test later. A test that
    passed in step 4 and fails now is new: STOP. The second command prints
    each new failure. If a test fails once, run that test file alone before
    you treat the failure as real, for example
    `pnpm test:run lib/admin/page-address-messages.test.tsx`.

15. Commit the upgrade on the upgrade branch:

    ```bash
    git add -A
    git commit -m "Upgrade formulacms to v0.1.1"
    ```

    If the person accepted known test failures, list them in the commit body.
    `grep '^ FAIL ' .git/formulacms-tests-after.txt` prints them.

    Then bring the branch into your main branch the way you usually do, for
    example with a pull request.

16. Deploy. The person deploys, with their usual deploy. An agent stops here.

## Conflict rules

A path can match more than one class. The first match in this order wins:

> releaseOnlyPaths > sharedRegistries (manifest, then generated files) >
> pathRules > an exact-path entry in any list > an ownerOwnedPaths glob > an
> engineOwnedPaths glob > defaultRule.

So `lib/slices/slices.manifest.json` follows the block registry rule, even
though `ownerOwnedPaths` also lists it. The exact `convex/lib/slices/*.ts`
entries in `engineOwnedPaths` are engine files inside your block folder.

| Class                         | Paths                                                                                                       | What to do                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shared registry manifest      | `convex/lib/contentTypes/content-types.manifest.json`, `lib/slices/slices.manifest.json`                    | "Keep both sides' entries in the manifest." Never take the whole file from one side: the regenerate command then deletes the other side's content types or blocks without an error.                                                                                                                                                               |
| Generated files of a registry | the `generated` lists in `engine.manifest.json`, for example `convex/schema.ts` and `lib/slices/builder.ts` | "Never edit the generated files by hand: take either side, then run the regenerate command and confirm the check command passes." For example, `git checkout --theirs -- <file>`, then step 9.                                                                                                                                                    |
| `package.json`                | `package.json`                                                                                              | "Keep both sides' dependency and script entries, one entry at a time. Never keep a whole conflicting block from one side. When one package changed on both sides, take the starter's version unless you pinned yours on purpose."                                                                                                                 |
| Lockfile                      | `pnpm-lock.yaml`                                                                                            | "Never edit it by hand. Resolve package.json first. Then take the starter's lockfile (git checkout --theirs pnpm-lock.yaml), or leave the conflict markers in, because pnpm removes them. Run pnpm install. Then pnpm install --frozen-lockfile must pass."                                                                                       |
| Public site and messages      | `app/(public)/**`, `messages/**`                                                                            | "Resolve each conflict on its own. Keep your text and styling, and keep the starter's new keys and fixes. Never take a whole file from one side."                                                                                                                                                                                                 |
| Owner files                   | `ownerOwnedPaths`: `app/globals.css`, `convex/lib/slices/*.ts`, `components/slices/**`, `public/**`         | Keep yours. Then review the starter's changes that merged without a conflict (step 13). An agent stops on a conflict here and shows the person both sides. It proposes to keep the person's change and add any part of the starter's change that does not alter the person's text or styling, such as a new attribute or fix. The person decides. |
| Engine files                  | `engineOwnedPaths`, for example `convex/**`, `scripts/**`, `components/admin/**`, `app/(core)/**`           | Take the starter's side (`git checkout --theirs -- <file>`). Then port your own edit back. An agent stops on sign-in and publication files.                                                                                                                                                                                                       |
| Everything else               | all other paths, including `README.md`                                                                      | "Resolve each conflict on its own. Keep your text and styling, and keep the starter's new keys and fixes. Never take a whole file from one side."                                                                                                                                                                                                 |

Three more facts:

- A file that only you added, such as your own content type module, never
  conflicts.
- When both sides changed the same label or sentence, your text wins. Read
  the starter's version first: if it fixes an error, bring the fix into your
  text.
- Never keep a whole conflicting hunk from one side in a shared file. A test
  of this upgrade method showed that this drops the starter's new entries,
  for example a new dependency or a new README sentence.

## A site without the starter's history

Use this section when step 3 fails. That happens with a downloaded copy or a
fresh `git init`.

1. If the folder is not a git repository yet, create one and commit your files:

   ```bash
   git init
   git add -A
   git commit -m "Site files"
   ```

2. Add the starter remote and fetch its tags, as in "Read this file from a
   0.1.0 site".

3. Prove that your site started from v0.1.0. The two values must be equal:

   ```bash
   grep '"generatedTreeDigest"' starter.release-lock.json
   git show v0.1.0:starter.release-lock.json | grep '"generatedTreeDigest"'
   ```

   If they differ, the base is not v0.1.0. STOP and ask.

4. Re-parent your files on v0.1.0. An agent asks the person first:

   ```bash
   git switch -c reconnected $(git commit-tree 'HEAD^{tree}' -p 'v0.1.0^{commit}' -m "Reconnect to formulacms v0.1.0")
   ```

5. Continue with step 4 of "Steps".

The `reconnected` branch does not share history with any branch you pushed
before. To publish it, you need a new branch name or a force-push. An agent
asks the person first.

## Roll back

This upgrade changes no data, so the 0.1.0 code runs on the same data.

- During the merge: `git merge --abort`.
- After the commit, before a deploy: switch back to your main branch with
  `git switch <your main branch>`. Delete `upgrade/0.1.1` when you no longer
  need it.
- After a deploy: deploy your previous commit again with your usual deploy.
